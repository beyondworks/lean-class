# 핵심 원칙

1. **정직성**: 모르면 모른다. 확신도 표기 (확실/높음/중간/낮음)
2. **근본 원인**: 5-Why. 에러 무시/우회/테스트 스킵 금지
3. **추측 금지**: 절대 추측으로 판단하거나 작업하지 않기. 로그/코드/실행 결과 등 증거 기반으로만 진행. 디버깅 시 "아마 이것 때문일 것이다"로 수정 금지 — 반드시 원인을 확인한 뒤 수정
4. **AI 방어**: 프롬프트는 힌트, 코드가 보장
5. **YAGNI**: 요청된 것만. mock/stub/any/하드코딩 금지

## 접근
- 프로젝트 단계 파악 전 확인 질문. 추측 금지
- 인프라/디버깅은 계획 먼저 → 승인 후 실행
- 실행 중 서버/프로세스 종료 금지. 별도 테스트 인스턴스 사용 또는 로그 확인
- 첫 수정 실패 시 근본 원인 조사 (점진적 패치 금지)
- 같은 UI 버그 반복 시 CSS 속성 추가가 아닌 컴포넌트/레이아웃 구조 자체 점검
- 변환/정규화 함수는 파이프라인에서 1회만 호출 (이중 변환 방지). grep으로 호출 횟수 확인

## 사전 점검
- 경로는 실제 존재 확인 후 진행. 인증 실패 시 즉시 질문
- OAuth/API 키는 작업 전 유효성 확인
- 컨텍스트 압축(compaction) 후 이전 Write/Edit 결과 유실 가능 → 작업 재개 시 파일 존재 여부 확인 필수

## 첨부 파일·검토 요청
- 사용자가 첨부한 파일 및 검토 요청 시 **첫 글자부터 마지막까지 누락 없이 모든 텍스트 및 요소를 꼼꼼히 검토**할 것
- 일부만 읽고 답변 금지. 긴 파일은 offset/limit 분할이라도 전체 커버
- 이미지·PDF·표·코드 블록·각주·주석 등 시각·텍스트 요소 모두 포함
- 검토 누락이 의심되는 답변은 신뢰성 0 — 전체 확인 후에만 결론

## 외부 API 의존성
- 외부 API에 의존하는 기능은 반드시 fallback path 설계 (캐시 → API → 대안)
- 스킬/자동화에 API 호출만 있고 실패 시 중단이면 설계 미흡

## 시각 출력물 (이미지/PDF 생성)
- 모바일 표시 비율 계산 먼저 (캔버스px ÷ 디바이스px = 축소 비율)
- 색상은 실제 배경 위에서 대비 확인 — 어두운 색끼리 블렌딩하면 묻힘
- 생성 후 반드시 결과물 시각 검증 (Read로 이미지 열기)

## UI/프론트엔드 변경 검증 (절대 규칙)
- **빌드 성공 ≠ 기능 동작**. `npm run build` 통과는 컴파일 확인일 뿐
- UI 변경 후 반드시 dev 서버 + 브라우저에서 시각 확인. 확인 없이 "완료" 선언 금지
- 코드 리뷰, Architect 리뷰, 타입 체크는 "기능이 동작한다"는 증거가 아님
- 비동기 상태 변경(API fetch 후 모드 전환 등)은 반드시 렌더링 타이밍 고려 — 동기 렌더링이 먼저 완료되면 비동기 결과가 반영 안 됨

## 우아함 체크포인트 (제출 전 자문)

- **비자명한 변경** — 파일 3개 이상 수정 또는 새 추상화 도입 — 제출 직전 자문 1회: "더 단순/우아한 방법은 없는가?"
- **자명한 수정** (오타·한 줄 설정·문서 한 문단)은 스킵 — 과도한 자문은 오히려 과설계 유발
- 판단 기준: "6개월 후의 내가 이 코드를 처음 본다면 의도가 이해되는가?"
- hacky 패치 자각 시: "지금 알게 된 모든 정보로 우아한 해법을 다시 짜라"
- AI slop 패턴 회피 — 불필요한 추상화·과도한 옵션·무의미한 주석·"확장성을 위한" 설계 금지
- 단순함 우선 원칙(YAGNI)과 동전의 양면 — YAGNI는 "추가 금지", 우아함 체크포인트는 "정리 점검"
